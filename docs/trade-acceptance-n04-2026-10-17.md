## Воспроизведённый дефект

В отдельной `cryptoanal_runtime_test_*` БД локальный TCP proxy пропускал подключение
и запрос, но удерживал уже полученный ответ PostgreSQL. Запрос `SELECT 42` был
выполнен; server statement timeout 100 мс не прервал ожидание клиента.
Через 400 мс Promise оставался незавершённым. После возврата 79 байт ответа
он завершился через 407,577 мс. На ожидание потерянного ответа server timeout не действует.

У worker были connect/transaction/server timeouts, но не было клиентского срока
ожидания ответа запросов. Это подтверждённый механизм бесконечного занятия слота;
он совместим со старым симптомом, но историческая причинная связь не доказана.

Клиенты с настроенными пулами теперь получают `query_timeout`. После `Query read timeout`
соединение закрывается, чтобы интерактивная транзакция не вернула зависшую protocol
сессию в пул. Одного отклонения Promise недостаточно: занятое соединение могло бы
сохраниться и блокировать следующие запросы.

Рабочие пределы отдельного SQL:

| Пул worker                             | Server statement timeout | Client response timeout |
| -------------------------------------- | -----------------------: | ----------------------: |
| trading / entry / protection / journal |                  4000 мс |                 6000 мс |
| background, включая funding/history    |                 20000 мс |                22000 мс |

Connect timeout 2000 мс, transaction maxWait 1000 мс и timeout 10000 мс сохранены.
Это разные ограничения; полный цикл нескольких запросов не ограничен одним из них.
Дополнительно server idle-in-transaction timeout 15000 мс освобождает брошенные
транзакции, если сервер не получил закрытие клиента. Он ограничивает простой между
SQL, а не полное время активной транзакции. API без явных настроек пула сохраняет прежнее поведение. Новых npm-зависимостей
и миграций нет. Параметры защиты, freshness, admission и торговые решения не менялись.

При потерянном ответе COMMIT результат остаётся неопределённым: БД могла сохранить
операцию. Драйвер не повторяет её автоматически. Прежние IDs, CAS, уникальность и
идемпотентность финансового пути должны определить итог следующей попытки.

## Проверка отказов и нагрузки

Локальный proxy действительно удерживал серверные ответы, а не подменял Promise
искусственной задержкой. При client timeout 250 мс и server timeout 100 мс:

- потерянный read response завершился ошибкой за 260,812 мс; следующий запрос
  прошёл по новому backend без перезапуска worker;
- потеря ответа внутри транзакции завершилась за 254,118 мс, запись откатилась;
  явный повтор сохранил единственную строку;
- потерянный ответ COMMIT сообщил ошибку, хотя строка уже сохранилась; автоматического
  повтора не было, последующая проверка/идемпотентный запрос не создали дубликат;
- дополнительно proxy удержал серверное соединение после закрытия клиента: risk lock
  ещё был занят после client timeout, затем сервер сам освободил его по idle deadline
  700 мс; от начала транзакции до освобождения прошло 718,699 мс, последующий запрос прошёл;
- обычная SQL ошибка откатывается до savepoint на том же здоровом соединении;
- при потере ответов во всех четырёх слотах следующий элемент обработан за 265,644 мс.

Финальный `pnpm runtime:verify`: **498/498**, без skips, две свежие изолированные БД.
Включён прежний профиль: burst 6000 событий, занятые пулы/БД, отказ backend,
медленная история, приоритетный первый выход, CAS и единственность денежных операций.
Финальные transport тесты: 7/7, включая потерянный disconnect. Typecheck, lint, format и build прошли.
Это результаты изолированных сценариев, не доказательство биржевого Demo исполнения.

## Измерения и диагностика

Latency v2 сохраняет общий отчёт и раздельные `startup`/`steady` распределения.
Startup — первые 300 с после создания коллектора; граница не освобождает от целей.
Recovery и replay остаются отдельными метриками; нагрузка сохраняется отдельным прогоном.
В каждом срезе есть начало окна, время выборки, число событий, p50/p95/p99 и максимум.
Окно остаётся до пяти минут, histogram quantiles — верхние границы интервалов.

Отрицательные значения не включаются в histogram длительности, но больше не исчезают
из критерия: считаются по имени метрики. При наличии таких событий статус
`clock-uncertain`. Для legacy v1 общий неатрибутированный счётчик также не позволяет
принять `market.deliveryMs`. Сырые `observedAt`/`receivedAt` последних восьми событий
сохраняются в отчёте отдельно; это ограниченная выборка, а не весь интервал.

До обновления `07:58:55.190Z` новый reader уже показал `clock-uncertain` вместо успеха:
178 положительных и 4052 legacy отрицательных наблюдения. В исходных событиях были
разности −191 и −190 мс. Часы и pinned freshness не изменялись.

При менее 100 наблюдениях соблюдённый предел обозначается `insufficient-samples`;
превышение показывается и на малой выборке. 100 — минимальный порог представления,
а не доказательство стабильного p99. Отсутствующий этап остаётся `unobserved`.

В heartbeat видны lane/key/startedAt/ageMs активных position/entry/funding задач,
последние завершения и ошибки. Возраст ожидания измеряется монотонными часами,
поэтому изменение календарных часов не уменьшает его. Завершение одного пути
не скрывает незавершённую задачу другого; эти данные помогают следующему разбору сбоя.
Счётчик `failed` относится к попыткам, завершившимся исключением, включая штатное
откладывание при занятости lock; это не число финансовых нарушений.
