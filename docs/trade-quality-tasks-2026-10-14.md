## 1. Общие правила работающего бота и validation

Завершено 15 октября. Порядок реализации:

- [x] Общий чистый расчёт account equity/exposure/stop budget/admission и торгового календаря.
- [x] Версионированный policy snapshot запуска/validation/позиции, история изменений защиты.
- [x] Validation/replay с тем же риском и дополнительной защитой, без использования будущего результата свечи при входах.
- [x] Классификация сравнимости и новые baseline-результаты без изменения старых метрик.
- [x] Проверки паритета, отчёт, коммит и контролируемое обновление DRY_RUN.

Проблема: runtime и validation используют разные правила портфельного риска,
дополнительной защиты прибыли и допуска новых входов. Их результаты нельзя
сравнивать как исполнение одной и той же конфигурации.

- [x] Описать и версионировать полный набор правил исполнения: стратегия, account safety, издержки, funding, нормализация инструмента и защита прибыли.
- [x] Сохранять эти правила в неизменяемом snapshot запуска и validation; фиксировать моменты включения и изменения политики.
- [x] Вынести общий расчёт equity, экспозиции, риска до стопов, размера позиции и дневного бюджета в application-слой.
- [x] Унифицировать торговые сутки и отдельно описать дополнительный UTC safety latch, его срабатывание и сброс.
- [x] Включить дополнительный безубыток/trailing в validation и replay с теми же правилами активации.
- [x] Сравнивать одинаковые наборы событий и правил; различия между OHLC и точной ценовой последовательностью показывать отдельно.
- [x] Создать новые validation результаты и baseline, сохранив прежние версии и метрики.

**Готово, когда:** одинаковые входные события и policy snapshot дают одинаковые
допуски входов, размеры, защитные уровни, денежные результаты и причины выхода.
Оставшиеся расхождения из-за недостаточной детализации OHLC явно классифицированы.

## 2. Биржевые шаги, округление и минимальные размеры

Проблема: `tickSize`, `qtyStep`, `minOrderQty`, `minNotional` доступны, но не
используются при расчёте исполнения. В проверенной выборке количество всех 414
позиций не соответствовало шагу инструмента.

- [x] Определить единые правила нормализации количества, входной цены, SL, TP и trailing с учётом стороны и назначения заявки.
- [x] Использовать точную десятичную арифметику для проверки кратности и округления; количество округлять без превышения бюджета риска.
- [x] После нормализации заново проверить риск, комиссии, экспозицию и валидность уровней.
- [x] Проверять минимальное количество и сумму заявки; учитывать ограничения максимального размера, если они применимы.
- [x] Блокировать вход при отсутствующих или устаревших обязательных параметрах инструмента с понятной причиной.
- [x] Сохранять использованные параметры инструмента в snapshot; историческая проверка не должна молча подставлять сегодняшние ограничения.
- [x] Применить одинаковые правила к runtime, validation и replay, не меняя старые сделки.

Новые validation используют закреплённый снимок ограничений как явный сценарий
для прошлого периода. Его допущение показано в отчёте; подтверждённой историей
правил биржи этот снимок не объявляется. Старые открытые позиции сохраняют прежние
правила до закрытия; ранее сохранённые сделки и validation не пересчитаны.

**Готово, когда:** новые количества и требуемые ценовые уровни соответствуют
биржевым шагам; итоговый риск не превышает бюджет. Проверены BTC, ETH, DOGE,
long/short, пограничные минимумы и размер, обнуляющийся после округления.

## 5. Recovery и закрытия при неопределённой истории

Выполнено 16 октября. Порядок реализации:

- [x] Снять read-only статистику выходов и качества сохранившейся истории.
- [x] Добавить ограниченное восстановление по публичным сделкам до OHLC fallback и журнал причин разрывов.
- [x] Согласовать recovery дополнительной защиты, исключить будущие цены и сохранить совместимость старого replay.
- [x] Проверить обе стороны, границы, restart/rollback; обновить отчёт и DRY_RUN, сделать коммит.

Проблема: в снимке 73 из 390 сделок закрыты через `recovery-exit`. Минутные свечи
не всегда позволяют восстановить порядок цен; все такие выходы нельзя автоматически
считать ошибками.

- [x] Разобрать причины сохранённых recovery-exit: reconnect, простой, overflow, недоступность истории и неоднозначная частичная минута. Для 70 старых выходов точная причина не сохранена и остаётся неизвестной.
- [x] Отдельно измерять частоту разрывов и источник неопределённости; сохранять события соединения и границы отсутствующих данных.

- [x] Проверять одинаковое восстановление SL, TP, strategy protection и дополнительной profit protection с учётом времени её включения.
- [x] Не восстанавливать неизвестные пики и исторические fills как подтверждённые; сохранять проверки доступности сигнальной истории.
- [x] Добавить архив и ограниченный public-trade источник для сокращения неопределённости, сохраняя безопасную обработку неизвестного интервала. Снижение частоты выходов на длительном периоде пока не измерено; нагрузочная устойчивость относится к пункту 6.

**Готово, когда:** для непрерывной подтверждённой истории recovery совпадает с
обычным replay. Для неполной истории причина и выбранный исход объяснимы;
безопасный прогресс сохраняется, новые входы блокируются при незавершённом recovery.

snapshots сохраняют прежний OHLC fallback. Следующий шаг — пункт 6.

не заявлены. Проверка часов источника вынесена в идеи без изменения timestamps/freshness.

## Идеи

Кандидаты для отдельного исследования после выполнения базовых пунктов. Их
реализация не входит в текущий обязательный объём без отдельного выбора:

- Расстояние SL/trailing через ATR вместо фиксированного процента или R.
- Фильтр минимального отношения чистой потенциальной прибыли к риску входа.
- Пауза между повторными входами или после серии убытков.
- Выбор торговых режимов по тренду старшего таймфрейма и рыночной волатильности.
- Контроль и сохраняемая модель смещения часов источника: в проверке 16 октября
  публичный server-time отставал от локального интервала на сотни миллисекунд.
  Не сдвигать исходные timestamps и не ослаблять pinned freshness gates без отдельной модели и проверки.
