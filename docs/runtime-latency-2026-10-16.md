## Изменения

- Входы и позиции имеют независимые циклы с ограниченным параллелизмом.
  Период учитывает длительность работы вместо добавления полного sleep после неё.
  Одна позиция не выполняется параллельно внутри своего обычного пути.
- При ожидании recovery или сигнальной истории работает отдельная защита.
  Она проверяет также позиции, ожидающие свободного обработчика, и сохранённые
  касания с последующим отскоком. Среди доступных цен выбирается первое условие
  выхода по уже подтверждённым уровням. Курсор быстрого поиска временный и не
  продвигает состояние позиции. Неизвестные пики не активируют trailing/безубыток.
- Подтверждённый приоритетный CAS прерывает медленный запрос истории. Конкурирующий
  старый обработчик не может перезаписать результат. Непроверенный интервал и
  сигнальные условия остаются явно неполными в trace; исторический fill не выдумывается.
- Writer, входы, сопровождение, защита и фоновые задачи получили отдельные пулы:
  **2 / 2 / 6 / 2 / 4** соединения, максимум 16 на worker. Это изоляция пулов,
  а не обещание физической изоляции общего CPU/диска.
- Worker берёт risk/runtime locks через try-lock. При конфликте транзакция
  откатывается, повтор ждёт вне БД до 250 мс, затем задача откладывается.
  Риск, CAS, статус и первоначальный TTL заново проверяются внутри транзакции.
  API сохраняет прежний режим ожидания. Работа по одной workspace всё ещё
  сериализуется тем же account risk lock.
- Журнал пишет по 500 событий, быстро продолжает непустую очередь и сохраняет
  целиком неудавшийся пакет. При ошибке backoff 50–1000 мс закрывает допуск входов.
  Отдельный writer pool имеет statement timeout 4 с, transaction timeout 10 с,
  maxWait 1 с и connection timeout 2 с. Это разные пределы; общий срок запроса
  не называется равным одному из них.
- Штатная остановка дожидается записи и начатых продлений lease, затем освобождает
  только собственный writer lease. Чужой lease не удаляется. При аварии остаётся
  прежний срок истечения 30 с.
- `runtime:latency` читает rolling p50/p95/p99 и счётчики этапов из heartbeat,
  возраст очереди, TTL/ожидания и состояния пулов. Квантили — верхние границы
  histogram buckets, окно до пяти минут, шаг 10 с. После restart история начинается
  заново; отсутствующие наблюдения остаются `unobserved`.

Новые defaults: входы каждые 250 мс, entry concurrency 2, проверка защиты каждые
100 мс, список защищаемых позиций обновляется каждые 500 мс. Период сопровождения
1000 мс и concurrency 4 сохранены. Политики стоимости, прибыли, funding и TTL не менялись.
Быстрый путь использует последний подтверждённый checkpoint; ещё не сохранённый
результат recovery не становится защитным уровнем во время следующего ожидания.

## Критерии и профиль проверки

Для текущих стратегий EMA/breakout/mean-reversion/momentum при обычной работе:

| Этап                                                   | Цель p99 |
| ------------------------------------------------------ | -------: |
| наблюдение рынка → локальный receive                   |  1000 мс |
| receive → запись public trade                          |   500 мс |
| receive → checkpoint позиции                           |  2000 мс |
| receive → checkpoint при восстановлении свежего потока |  5000 мс |
| receive → приоритетная защита                          |  1000 мс |
| receive → вход по свежей цене                          |  1000 мс |

Последние два предела согласованы с текущим default book-age 1000 мс; закреплённые
правила конкретной заявки проверяются независимо от статистики. Finality-to-fill
показывается по семейству и типу ордера: limit waiting не смешивается с market.
Задержка получения закрытой свечи измеряется отдельно и зависит от публичного источника.
Метрики ожидания/отказов считают попытки, если не указано committed fill/terminal decision.
Истечение limit TTL не доказывает, что задержка worker сорвала существовавший fill.

Изолированный приёмочный профиль: 12 открытых позиций, 8 ожидающих входов одного
account, 6000 цен одним burst, затем 20 свежих цен и одно защитное касание.
Пакет 500, position concurrency 4, entry concurrency 2. Все позиции risk-coupled;
повтор после занятости не ослабляет общий лимит. PostgreSQL backend writer реально
завершён, пока INSERT ждал блокировку таблицы. После rollback вся очередь повторена.
Два фоновых соединения заняты, четыре задачи ждут имитацию истории по 500 мс.
Отдельно проверены приоритетный выход, единственность Trade и отказ старого CAS.
Для экстремального burst допуск receive-to-journal расширен до **2000 мс**;
пределы входа, защиты и checkpoint остаются 1000/1000/2000 мс.

Docker окружение: **4 CPU, 6210576384 байт RAM**. Нагрузочная БД отличается от БД
persistence suite. Обе имеют префикс `cryptoanal_runtime_test_*`; рабочая база запрещена.
Сценарий использует синтетический LastPrice и старую entry basis для проверки
очередности, транзакций и риска. Он не моделирует реальную биржевую очередь/L1 fills.
Существующие интеграционные тесты отдельно проверяют IOC/PostOnly и receipts.

`pnpm runtime:load` требует `RUNTIME_LOAD_DATABASE_URL` с применёнными миграциями;
`RUNTIME_LOAD_REPORT_PATH` сохраняет JSON, в том числе перед проваленной latency assertion.
Это конечный профиль, не оценка максимальной устойчивой пропускной способности.

## Нагрузка и restore-check

Параллельный restore-check восстановил полный dump 680618863 байт в отдельном
контейнере с **1 CPU / 768 МиБ RAM**. Источник не подключался к восстановленной БД.
При отдельном нагрузочном прогоне во время восстановления:

| Этап                          | p50, мс | p95, мс | p99, мс | максимум, мс |
| ----------------------------- | ------: | ------: | ------: | -----------: |
| запись пакета                 |      50 |     100 |     100 |         55,8 |
| receive → журнал, 6000 цен    |     500 |    1000 |    1000 |          622 |
| свежая цена → вход, 8 fills   |     250 |     250 |     250 |          222 |
| цена → checkpoint, 12 позиций |    1000 |    2000 |    2000 |         1132 |
| приоритетный выход, 1 касание |      50 |      50 |      50 |           35 |

Burst записан за 555 мс. Нет потерянных событий, дублей выхода или успешной записи
устаревшего CAS; все 8 входов выполнены. Один защитный замер — функциональная проверка
и максимум конкретного случая, а не репрезентативное распределение защитных выходов.
Файл — `var/analysis/latency-load-during-restore-2026-10-16.json`.

**Граница:** при одновременных full runtime suite, нагрузочном прогоне и restore-check
с созданием индексов журнал однажды превысил burst p99 2000 мс. Все восемь входов,
двенадцать checkpoint и единственный приоритетный выход сохранили целостность;
точное значение проваленного percentile старая версия теста не сохранила.
Наблюдение записано в `var/analysis/latency-overload-observation-2026-10-16.json`.
Успешный отдельный прогон не отменяет этот предел CPU/диска хоста. Сочетание всей
suite и обслуживания БД не входит в подтверждённый эксплуатационный профиль.
Параллельные full suite также требуют свежих изолированных БД: фиксированные archive
fixtures нельзя повторно выполнять поверх оставшихся данных.

## Рабочий поток и границы измерения времени

В наблюдаемом окне `2026-10-16T04:09:38.370Z`: 11010 записанных цен,
3241 checkpoint, p99 receive-to-journal **250 мс**, обычного сопровождения
**2000 мс**, очередь 0. Входов и приоритетных выходов в этом окне не было:
их production-like latency остаётся `unobserved`; функциональное и нагрузочное
доказательство для них дано отдельной БД. В текущих позициях наблюдались EMA,
breakout и momentum; это не live latency всех четырёх семейств.

Сырой `market.deliveryMs` — разница временных меток Bybit и локального receive.
В том же окне histogram p99 **2000 мс**, максимум **1204 мс**: цель raw age 1000 мс
не подтвердилась. Это не доказанная односторонняя задержка сети. Отдельный точный
read-only подсчёт по журналу в соседнем пятиминутном окне `04:08:42.806Z`
дал p50/p95/p99 **634 / 657 / 978,75 мс**, максимум 1204 мс; перекрытие пяти минут
проверено по ограниченной выборке последних 50000 событий.

Пять запросов recent trades и пять запросов публичного `/v5/market/time` с
уникальным query/cache-control выявили расхождение шкал времени. У коротких
server-time запросов RTT **285–288 мс**, возможный интервал server-minus-local
примерно **−631…−342 мс** при предположении timestamp внутри запроса; CloudFront
сообщил Miss. Это оценка с асимметрией пути/семантикой серверной метки, а не NTP
калибровка. Контейнер и host не показали сопоставимого с этим расхождения:
совместимый интервал container-minus-host около **−8…62 мс**.
Измеренные границы сохранены в `latency-{clock-probe,server-time-probe,docker-clock}-2026-10-16.json`.

Системные часы, исходные trade timestamps и pinned freshness не корректировались.
Модель сохраняемой калибровки часов вынесена в идеи; её нельзя молча применить
к старым proof/сделкам. Успех локальных latency gates не заявляется доказательством
внешней транспортной задержки или готовности Demo/Live.

Стартовое восстановление свежего потока, старый journal replay и обычные checkpoint
измеряются отдельно. Консервативная защитная обработка во время неизвестной истории
сохраняет `incomplete`, даже если найдено достоверное касание.

## Применение и сохранность

Пересобраны только API/worker, схема осталась на 43 миграциях. При первом переходе
с 0.11 старый lease освобождён только после подтверждения остановки его owner.
Штатный restart 0.12 затем проверен на рабочем DRY_RUN: lease удалился автоматически,
ручное удаление не потребовалось (`latency-graceful-restart-2026-10-16.json`).

Read-only проверка подтвердила неизменность **419** исходных Trade, **189** завершённых
ValidationRun, **34** ExecutionRun contexts, **41** snapshot hashes и входных
параметров **439** позиций. Включены все 418 Trade первого среза.
Старый закрытый trace `737b6dae-52bc-40cf-b178-e46a1007b500` воспроизведён
с `matched` на **264007** событиях, без расхождений денежного результата/receipts.
Исходные результаты и snapshots не пересчитывались.

Финальная сборка сверена в обоих контейнерах: **21** runtime/schema/lock/scripts файл,
общий SHA-256 `5f62c964e4d8d92e92b437f89fb94b9a90c3f289a052c2185cb292f1721e85b0`,
расхождений нет. API/dashboard возвращают HTTP 200. В срезе `04:17:15.145Z`
Health healthy, **34 DRY_RUN/RUNNING**, **20/20** защищённых позиций, 137 курсоров
без ошибок, 43 миграции без ошибок. В логах финального worker нет ошибок уровня 50+.

После прогрева, `04:19:00.975Z`: 5366 цен и 1478 обычных checkpoint, p99 журнала
**500 мс**, обычного сопровождения **2000 мс**, двадцати recovery checkpoint
**5000 мс** (фактический максимум recovery 2102 мс); очередь 0. На малой стартовой
выборке p99 обычных checkpoint временно превысил цель, максимум **6352 мс**.
Этот максимум не скрыт успешным p99 более длинного окна. Входы/приоритетные выходы
в рабочем окне остались unobserved; гарантии для них ограничены тестовым профилем.

Последний load-прогон дополнительно удерживает настоящий workspace risk lock
400 мс во время защитного запроса: первая исчерпанная попытка не прерывает историю,
следующая после освобождения делает CAS и единственный выход. Измерено **443 мс** при удержании risk lock 400 мс; цель ≤1000 мс
проверяется по фактическому receive-to-commit. Обе временные тестовые БД удаляются
после проверки; исходная БД ими не подменялась.

Переполнение очереди ограничено эпизодами: 10000 последовательных отказов enqueue
создают один разрыв потока, а не 10000 записей metadata/Promises. Каждый
отброшенный trade считается отдельно; новый эпизод начинается после принятой цены.
