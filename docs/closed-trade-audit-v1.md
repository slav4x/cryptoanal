# Автоматическая проверка закрытых сделок v1

N02 из [рабочего списка](trade-acceptance-tasks-2026-10-16.md).
Версия проверяющего кода: `cryptoanal-closed-trade-audit@1`.
Используется [контракт N01](trade-acceptance-contract-v1.md) и закреплённая граница
`var/analysis/acceptance-n01-2026-10-16.json`.

## Запуск

```bash
pnpm runtime:audit-trades development var/analysis/acceptance-n01-2026-10-16.json var/analysis/trade-audit-n02-2026-10-17.json
```

Последний необязательный аргумент — Position ID для проверки одной закрытой
позиции. Полный запуск фиксирует все видимые закрытия DRY_RUN на asOf и список их
ID; старые закрытия, перенесённые позиции и новые входы разделены относительно N01.
Новый capture N01 для каждого запуска не требуется.

Команда работает через read-only PostgreSQL URL, проверяет режим и использует
не более двух соединений с statement timeout 20 с. Заявки, позиции, Trade,
validation и runtime settings не изменяются. До/после проверяются прежние Trade,
завершённые validation, context запусков и trace snapshot hashes.

Результат — новый JSON и соседняя директория `<report.json>.evidence`.
Существующие файлы не перезаписываются; новый запуск требует другого пути.
Файлы доказательств имеют права 0600. Ключи и connection strings не экспортируются.
Новых зависимостей нет. Ошибка одной сделки записывается отдельно и не пропускает
остальную группу. Фоновая обработка, retry/checkpoint и retention-контроль — N03.

## Что проверяется

- Привязки Trade/Position/run/strategy version/config/policy, статус и времена.
- Первоначальные SL/TP по конфигу и закреплённому шагу инструмента, когда сохранён
  исходный entry checkpoint; текущий перемещённый стоп не подменяет начальный риск.
- Entry receipts: собственные IOC/PostOnly правила движка, TTL по времени события
  и получения, bid/ask/L1, источник ликвидности, fees и полный/частичный fill.
  Отдельно проверяется время сохранённого OPEN decision относительно pinned expiry.
- Финальность входа по исходному событию `runtime.signal.observed`, если оно
  сохранилось; время свечи не объявляется временем доступности сигнала.
- Exit trigger и liquidity receipts, объёмы/цены/fees, исходная модель, остаток,
  распределение издержек и funding через существующие proof verifiers.
- Conservation количеств и fees, взвешенные цены входа/выхода, Trade gross/net,
  Position realized PnL и funding payment receipts/дубли. Slippage не вычитается
  второй раз из уже исполненной цены.
- Исходный replay через `replayRuntimeTrace` и тот же price processor, который
  сопровождает runtime: приоритеты, защита/пики, signal finality, holding deadline,
  recovery inputs, partial exits и funding chain.
- Checksums snapshot/records/ценовых страниц; отсутствие префикса/хвоста,
  смена stream, gaps и recorded recovery не скрываются совпавшим итоговым PnL.

Каждая проверка содержит expected/actual и ссылки на Trade, Position, Order,
Fill, trace или исходное signal/funding событие. Есть отдельные статусы случаев
N01, диапазон событий и стадии: наблюдённый trigger, отправки, fills, завершение.
Первое допустимое срабатывание подтверждается только полным непрерывным replay;
при OHLC/recovery поле `firstEligibleTrigger` остаётся неизвестным.

Новая decimal liquidity-модель сравнивает денежные суммы точно. Legacy получает
только [исходные допуски N01](trade-acceptance-contract-v1.md#допуски);
округление средневзвешенной цены новой модели ограничено 18 знаками.

## Доказанность и ограничения

`matched` replay подтверждает выполнение записанной модели от сохранённого
checkpoint. Полный исходный путь требует fullFromEntry, совпавшего replay,
continuous history и одного stream. Metadata fullFromEntry или восстановленные
минуты сами по себе этого не доказывают.

Отсутствующая информация даёт `insufficient-data`. Доказанный локальный дефект —
неверная сумма, дубль fill, повреждённый checksum — остаётся `violation` даже при
отсутствии остального пути. Неизвестная версия/потеря исходного источника отличается
от checksum или semantic mismatch. Убыточная сделка сама по себе не является ошибкой.

Существующие источники не закрепляют состояние всего счёта под admission lock
в момент исполнения и переход общего cash/equity для каждой отдельной сделки.
Эти поля явно остаются unknown: финальный Trade и более ранний signal context
не позволяют восстановить их точно. N02 проверяет доступные финансовые инварианты
позиции и не выдаёт их за проверку всего исторического аккаунта.
Пригодные исходные доказательства для дальнейшего накопления нужно сохранять в N03.

Проверка restart требует исходных состояний до/после, а не только stream change.
Случай без наблюдённого события или известной применимости не объявляется пройденным.
Положительные частичные проверки отображаются отдельно от общего вердикта.
Код возврата 0 означает отсутствие найденных нарушений и ошибок загрузки сделки
целиком, а не подтверждение всех неизвестных случаев. Недоступная страница цены,
funding snapshot или исчерпанный бюджет остаются unknown с причиной в checks.
Нарушение, ошибка загрузки сделки целиком или изменение исходного cohort приводит
к коду 1 и сохранённому отчёту; повтор временно недоступных источников относится к N03.

## Повтор без рабочей БД

```bash
pnpm runtime:audit-trades --replay var/analysis/trade-audit-n02-2026-10-17.json <position-id>
```

Рядом с результатом сохраняются JSON исходной позиции, Trade, конфиг, run,
заявки/fills/payments, signal evidence, trace/records и manifest. Каждая использованная
страница цен — gzip архива существующего codec, с диапазоном, количеством и SHA256.
Funding snapshots сохраняются с hashes. Сохраняются SHA256 реализации и входов;
replay требует ту же реализацию и сравнивает checksum повторного результата.

Цены читаются страницами до 10000 событий, последовательно по позициям.
Бюджет — 4 млн прочитанных событий на позицию, проверяемый перед очередной страницей;
префикс/полный проход могут читать один интервал повторно. Исчерпание бюджета
сохраняется как недостаточность данных и воспроизводится без БД. Оно не превращается
в подтверждение пути. Сохраняемые страницы ограничены 32 МиБ распакованных данных
существующим codec; это ограниченная исследовательская команда, не load acceptance.

Результат, manifest, исходники и архивы проверяются перед использованием.
Подмена любого из них не должна давать прежний успешный результат.
Повтор не загружает новое состояние БД и не подмешивает более поздние цены.
