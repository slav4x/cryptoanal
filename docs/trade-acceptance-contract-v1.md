# Контракт приёмки сделок v1

N01 из [нового пула задач](trade-acceptance-tasks-2026-10-16.md).
Версия: `cryptoanal-trade-acceptance@1`.
Машиночитаемые правила — `packages/application/src/trade-acceptance.ts`.
Контракт задаёт классификацию; получение и проверка доказательств каждой сделки — N02.

## Исходный срез и граница новых данных

```bash
pnpm runtime:acceptance-snapshot development var/analysis/acceptance-n01-2026-10-16.json
pnpm runtime:acceptance-snapshot --verify var/analysis/acceptance-n01-2026-10-16.json
```

Capture читает один PostgreSQL snapshot в `REPEATABLE READ READ ONLY` на одном
соединении с принудительным read-only URL и проверкой режима. Тайм-аут запроса — 20 с.
Создаётся новый JSON с правами 0600, существующий файл не перезаписывается.
Пароли, ключи и connection strings не экспортируются. Новых зависимостей нет.

В снимке сохраняются стратегии/конфиги, deployments/runs/policies, позиции и Trade,
baseline, IDs/hashes завершённых validation, trace metadata и hashes записей,
cursors, открытые incidents, funding coverage, диапазоны горячего журнала и архива,
последние цены/времена receive, heartbeat/очереди/latency и миграции.
Сохраняются database visibility snapshot и asOf, Git revision, SHA256 реализации,
контракта, источников и полного результата. Суммы Decimal остаются строками.

MD5 исходных строк/JSON и списков hashes — дополнительные контрольные идентификаторы;
checksum экспорта — SHA256. Наличие chunk/hash/fullFromEntry в metadata не доказывает
целостность payload и непрерывность пути: они подлежат проверке N02.
Исходные tick payloads не входят в этот metadata-экспорт.

`--verify` не обращается к БД: проверяет checksums/версию контракта и повторно
рассчитывает границу и матрицу по сохранённым источникам. Для дальнейших проверок
использовать закреплённый файл; новый capture создаёт другую группу наблюдений.

| Группа            | Правило                                                                                                                |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------- |
| baseline-closed   | Trade ID уже присутствовал; не новое испытание.                                                                        |
| baseline-position | Position ID уже присутствовал; последующее закрытие старой открытой позиции учитывается отдельно от нового входа.      |
| late-discovered   | ID отсутствовал, но openedAt или createdAt не позже границы: запоздавшая запись/видимость, не новое forward-испытание. |
| new-entry-pinned  | Вход и создание позже границы, ID новые, run/version/config/policy совпадают с закреплёнными.                          |
| new-policy-entry  | Новый вход с иным run, strategy version, config или policy; отдельное испытание.                                       |

При равном времени — консервативное `late-discovered`. IDs исходного среза имеют
приоритет перед временем. Позднее обнаружение не превращает старый вход в новый.

## Группы и матрица

Разделять execution run, strategy version/config hash, символ, сторону, timeframe,
execution policy fingerprint и fingerprint моделей. Последний отделяет trace/run
engine, position-exit/recovery/exit/funding, правила инструмента и ключ защиты прибыли.
Время наблюдения instrument metadata исключено из fingerprint, сами шаги/минимумы
сохранены. Смену правил внутри жизни позиции N02 дополнительно проверяет по trace
records; финальный checkpoint не объявляется политикой всей истории.

Функциональный минимум — один подтверждённый случай в каждой применимой группе
для каждой стороны. Это не статистическая приёмка и не подтверждение скорости.
Четыре семейства сигналов разделяются через config/strategy identities; независимые
виртуальные аккаунты не складываются как портфель.

| Случай          | Обязательные доказательства сверх исходных IDs/policy                                             |
| --------------- | ------------------------------------------------------------------------------------------------- |
| market-entry    | Намерение, доступный сигнал, admission, public trade/L1, fills и защита остатка.                  |
| limit-entry     | То же плюс цена лимита, исходный TTL, отмена/исполнение без продления срока.                      |
| full-entry      | Requested/filled quantity, receipts и отсутствие потерянного остатка.                             |
| partial-entry   | Частичный fill, отменённый остаток и защита фактического объёма.                                  |
| stop-loss       | Начальный риск, непрерывный путь, первый допустимый trigger, exit intent/fills/ledger.            |
| take-profit     | То же; trigger level отделён от цены market fill.                                                 |
| break-even      | Момент включения, последующий пик, уровень с издержками и checkpoints.                            |
| trailing        | Пик после включения, перенос без ухудшения защиты, первый trigger и остаток.                      |
| signal-exit     | Исходные свечи/finality/availableAt, модель отмены идеи и исполнимая цена события.                |
| holding-timeout | Pinned deadline от исполненного входа, первая допустимая цена и причины ожидания.                 |
| partial-exit    | Попытки/fills, сохранённое намерение, остаток/защита и распределение fees/funding.                |
| recovery        | Границы разрыва, исходные восстановительные входы, непрерывность checkpoint и допустимый порядок. |
| restart         | Состояния до/после restart, повтор событий, единственность fills/Trade и защита остатка.          |
| settlement      | Количества/fills/fees/funding, cash/equity и Trade без двойного вычета slippage.                  |

Итого 28 пар «случай × сторона» до разделения на версии/символы.
`candidatePositions` — инвентаризация признаков, не число проверенных сделок.
Для break-even/restart capture не выводит события по косвенным признакам: нулевой
счётчик не доказывает отсутствие срабатываний. N01 не запускает N02, поэтому
`confirmed=0`, все ячейки пока `insufficient-data`.

## Статусы и порядок

- `confirmed`: применимость подтверждена, все обязательные проверки прошли с
  непустыми ссылками на проверенные доказательства и требуемые источники доступны.
- `violation`: есть конкретная проваленная проверка со ссылками на доказательства.
  Доказанное локальное нарушение сохраняется при неполноте другого участка истории.
- `insufficient-data`: неизвестна применимость, нет проверки/ссылки/источника.
  Отсутствующий trigger и неполный путь не означают успешную проверку.
- `not-applicable`: pinned политика/конфиг доказывает неприменимость правила.
  Отсутствия наблюдений недостаточно. Доказанное нарушение имеет приоритет.

Классификатор принимает результаты выполненных проверок; наличие строки с ID
само по себе не проверяет источник. Получение доказательств реализуется в N02.
Повтор и порядок проверок не меняют классификацию. Дубли/неизвестные проверки
отклоняются, чтобы не скрывать противоречивые результаты.

Для одного события действующей позиции: сохранённый exit intent → SL/trailing
или TP → срок → доступный сигнал → перенос защиты. Среди SL/trailing выбирается
более сильный уровень, при равенстве причина SL. Account safety независим:
первое сохранённое под locks/CAS намерение сохраняет причину, второй путь не
создаёт дубликат. [Подробности правил выходов](position-exits-2026-10-16.md).

## Допуски

Сохраняются допуски существующих проверяющих путей; единый более широкий допуск
для прохождения приёмки не добавляется:

- новые количества, шаги, receipts и бухгалтерские суммы — pinned decimal-модель
  до 18 знаков, без относительной погрешности, скрывающей превышение шага;
- legacy Trade net: `0.00000002`; legacy gross:
  `quantity * 0.000000005 + 0.00000002` из-за прежнего округления цены;
- legacy replay settlement: `0.0000001`; replay protection:
  `max(1e-9, entryPrice * 1e-12)`;
- открытая защита в ledger: `max(1e-10, entryPrice * 1e-12)`;
- IDs, порядок и времена исходных событий — точное совпадение с применимой моделью.
  Часы не сдвигаются, freshness gates не ослабляются.

Численный допуск не делает цену исполнимой. Незнакомая версия, потеря архива и
неоднозначный OHLC-порядок остаются явными ограничениями.
