# Продуктовая цель и границы этапов

## 1. Цель CryptoAnal

CryptoAnal должен стать клиентской платформой, в которой пользователь может пройти
полный цикл работы со стратегией:

1. выбрать рынок и торговую вселенную;
2. создать или скопировать стратегию;
3. зафиксировать её версию и параметры;
4. проверить на backtest и walk-forward;
5. запустить в выбранном режиме;
6. наблюдать позиции и решения;
7. разобрать результат по метрикам, сделкам, режимам и причинам;
8. сохранить выводы в журнале и playbook.

На первом этапе весь цикл доступен одному development workspace. Архитектура данных и
use cases сразу принимает `workspaceId`, но реальных пользователей ещё нет.

## 2. Приоритеты

### P0 — полноценный dashboard

Dashboard не является демонстрацией. Он должен содержать рабочие функции текущего
проекта, но с понятной навигацией, едиными контрактами и нормальными границами модулей.

В P0 входят:

- overview состояния системы и ключевых метрик;
- список пар, watchlist и подробная страница пары;
- открытые позиции, история сделок и карточка сделки;
- каталог стратегий, editor, версии, diff и управление запуском;
- Validation Center: backtest, walk-forward, сравнение прогонов;
- analytics: PnL, PF, expectancy, drawdown, R, MFE/MAE, breakdowns;
- health/drift/watchdog;
- explainability/activity;
- journal и playbooks;
- системные логи, runtime controls и настройки;
- единая дизайн-система на shadcn и semantic tokens.

### P1 — настоящая клиентская модель

После готовности dashboard добавляются:

- регистрация и вход;
- сессии и восстановление доступа;
- users, workspaces и membership;
- строгая изоляция данных;
- персональные стратегии, validation runs, сделки, журнал и настройки;
- подключения биржевых аккаунтов и безопасное хранение credentials;
- роли владельца и участника, если подтверждена командная работа.

### P2 — маркетинговый контур

После стабилизации P1:

- лендинг;
- методология и документация продукта;
- публичный санитизированный track record;
- формы интереса/регистрации;
- тарифы и billing — отдельным решением, не автоматически.

## 3. Основной пользователь dashboard

На первом этапе это разработчик/аналитик, который управляет одной средой. После P1 —
трейдер или исследователь, работающий внутри своего workspace.

Ему важно:

- быстро понимать состояние рынка, стратегий и исполнения;
- видеть, откуда появилась каждая цифра;
- не смешивать результаты разных конфигураций и datasets;
- сравнивать версии и прогоны;
- безопасно выполнять управляющие действия;
- возвращаться к выводам, а не только к графику PnL.

## 4. Продуктовые принципы

1. **Воспроизводимость.** Результат всегда связан с версией стратегии, dataset,
   execution model и engine version.
2. **Объяснимость.** Решение `OPEN/CLOSE/HOLD/SKIP` имеет причины и исходные факторы.
3. **Единая семантика.** Runtime и validation используют одни доменные правила.
4. **Честные данные.** Demo/live/backtest не смешиваются и всегда обозначены.
5. **Workspace ownership.** Пользовательские данные получают `workspaceId` с первого дня.
6. **Безопасные действия.** Опасные операции требуют явного подтверждения и audit event.
7. **Progressive disclosure.** Сначала ответ, затем детали и raw data.

## 5. Границы dashboard-first этапа

### Входит

- один фиксированный workspace;
- полный рабочий dashboard;
- один runtime deployment;
- Bybit как первый exchange adapter;
- paper/demo как основной режим разработки;
- все ключевые analytics и validation workflows;
- временный development access gate для удалённого стенда;
- schema-first API и ownership-ready storage.

### Не входит

- реальная регистрация и управление пользователями;
- OAuth, magic links, MFA и social login;
- workspace switcher и приглашения;
- пользовательский billing;
- публичный лендинг и отдельный public API;
- marketplace и продажа стратегий;
- копирование сделок других пользователей;
- мобильное приложение;
- несколько exchange adapters;
- обещание полноценного multi-strategy исполнения.

## 6. Переход от development identity к users

P0 использовал фиксированный контекст:

```text
actorId = development-operator
workspaceId = development
role = owner
```

В P1 fixed resolver удалён. Теперь сервер строит тот же context из database session и
membership, а UI по-прежнему не подставляет `workspaceId` в предметные запросы. Детали
зафиксированы в `13-AUTH-WORKSPACE-ARCHITECTURE.md`.

## 7. Стратегии

В продукте должны различаться:

- `Strategy` — стабильная сущность с названием, статусом и назначением;
- `StrategyVersion` — immutable snapshot конфигурации;
- `ValidationRun` — проверка конкретной версии;
- `Deployment` — привязка версии к runtime и режиму;
- `ExecutionRun` — конкретная сессия исполнения;
- `Trade` — результат внутри execution run.

Новая версия создаётся при любом изменении торговой логики. Существующая версия не
редактируется задним числом.

## 8. Multi-strategy

UI и данные можно подготовить к нескольким стратегиям, но первая реализация runtime
должна честно поддерживать один активный deployment на execution account, пока не готовы:

- allocation и reservation капитала;
- conflict resolution;
- суммарные лимиты риска;
- attribution позиции и сделки;
- независимая остановка каждой стратегии;
- тесты конкурентного исполнения.

## 9. Метрики успеха этапов

### Dashboard готов, когда

- все основные workflows выполняются без перехода к scripts/CLI;
- любая сделка трассируется до версии стратегии и execution run;
- любой validation result воспроизводим;
- route-level loading/error/empty states единообразны;
- нет глобального polling и ручного дублирования DTO;
- дизайн меняется через semantic tokens;
- dangerous actions и raw system data отделены от ежедневного сценария.

### Users/workspaces готовы, когда

- запрос без membership не читает и не изменяет чужие данные;
- все пользовательские сущности изолированы workspace;
- exchange credentials шифруются и никогда не возвращаются клиенту;
- audit trail фиксирует входы и управляющие действия;
- миграция fixed development workspace выполнена без потери истории.

### Landing готов, когда

- формулировки отражают реально работающий dashboard;
- public metrics строятся только из одобренной проекции;
- продукт не раскрывает приватные параметры, позиции или account data;
- маркетинговые обещания подтверждаются возможностями P1.

## 10. Не продуктовые цели

На рестарте не нужно максимизировать число функций или сохранить весь старый backlog.
Цель — получить связный, расширяемый dashboard и надёжную основу для клиентских данных.
